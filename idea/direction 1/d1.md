# 方向一：可执行技术实现路线

## 目标定位

实现一个以工具调用结果为主、联合用户行为与手动配置的偏好记忆系统，要求：
- 自动从多源事件中提取稳定偏好；
- 对偏好进行差分式版本管理与历史回溯；
- 支持跨场景初始适配与冷启动；
- 结果可直接约束后续工具调用参数，满足“偏好提取准确率≥85%”评测目标。

本实现方案要从“抽象流水线 + 版本管理 + 冲突消解 + 检索适配”落到具体模块、算法与模型层面。

## 1. 多源事件标准化与预处理

### 1.1 数据源与统一结构

统一输入类型为 `MemoryEvent`（见 `memoryhub/adapter/schemas.py`）：
- `tool_call`：工具执行结果及参数、输出文本、执行状态；
- `user_feedback`：显式偏好、纠错、覆盖指令；
- `user_behavior`：操作行为、点击/选择、跟随反馈；
- `manual_config`：用户配置项；
- `task_trajectory`：工具调用链、任务执行步骤。

### 1.2 预处理实现点（含具体算法）

在 `memoryhub/core/ingestion/` 里实现以下组件并给出明确算法：

- `DataCleaner.clean()`：字段规范与去重算法
  - 输入：原始事件 JSON
  - 步骤：
    1. 校验必填字段（`user_id`,`event_type`,`timestamp`,`content.tool_name`（若为 `tool_call`））；缺失则标记 `quality_score=0.0` 并返回短期记忆。
    2. 标准化 ID/时间格式（ISO8601）、字段名映射表（支持 alias 字段）。
    3. 去重判定：计算 `event_signature = sha256(user_id + source + tool_name + sorted(params))`；若在短时间窗（默认 60s）内存在相同 signature，则视为重复，合并 evidences 并丢弃新事件或将其作为重复证据合并进旧事件。

- `DataNormalizer.normalize()`：规范化字段与候选特征抽取
  - 目标输出为 `MemoryEvent` 结构中的 `content` 字段满足：
    {
      "tool_name": str,
      "params": {k: v},
      "output_text": str,
      "status": "success"|"failed",
      "candidate_features": {feature_name: feature_value}
    }
  - 映射规则（伪代码）：
    - if event.source == "calendar": map fields -> tool_name="calendar_read", params={range, calendar_id}
    - for params: normalize types (数字转数值，枚举小写化)，排序 key 并 stringify 用于 signature
    - candidate_features 从 `tool_name -> potential_preference_keys` 字典中抽取，如 `file_search` → [`result_format`,`search_scope`,`sort_order`]。

- `QualityScorer.score()`：明确评分公式与伪代码
  - 目标：为每个事件输出 `quality_score \b[0,1]`，用于判断是否进入长期记忆与是否作为偏好证据。
  - 因子定义：
    - completeness (C)：必需字段存在比例，0~1
    - success (S)：执行成功为 1，失败或异常为 0，若无状态信息用 0.5 作为中性值
    - semantic_coherence (M)：基于 embedding 的输出一致性（参考下文）
    - source_trust (T)：按来源赋值（`manual_config=1.0`,`user_feedback=0.9`,`tool_call=0.6`,`user_behavior=0.4`）
  - 合成公式（sigmoid 归一化）：
    - raw = w1*C + w2*S + w3*M + w4*T
    - quality_score = sigmoid( alpha*(raw - beta) )
    - 默认参数：w1=0.35,w2=0.3,w3=0.25,w4=0.1, alpha=5.0, beta=0.5
  - semantic_coherence (M) 计算：
    1. 如果可获得历史同类事件输出（n>=2），计算新的 `output_text` 向量与历史向量的平均余弦相似度作为 M；
    2. 若无 embedding 后端，使用启发式：非空且长度>20 字符 → 0.6，短文本或空 → 0.2。
  - 阈值应用：
    - quality_score >= 0.6：可作为长期证据并进入偏好抽取流程；
    - 0.4 <= quality_score < 0.6：进入中期队列，等待更多证据；
    - quality_score < 0.4：写入短期记忆或忽略偏好提取。

  - 伪代码：
    ```python
    def score(event):
        C = completeness(event)
        S = success_flag(event)
        M = semantic_coherence(event)
        T = source_trust(event.source)
        raw = 0.35*C + 0.3*S + 0.25*M + 0.1*T
        return sigmoid(5*(raw-0.5))
    ```

- `SensitiveDetector.detect()`：检测与处理策略
  - 使用配置中的正则集合（见 `docs/CONFIGURATION.md`）匹配 `content` 与 `output_text`。
  - 若命中 `HIGH` 级别规则且 `reject_on_detect=True`：拒绝入库并返回警告。
  - 若 `auto_mask=True`：对敏感串执行掩码（保留前后 2 字符，其余替换为 `*`），并将原文作为证据链单独存储于 `EvidenceStore`（加密/审计）。

### 1.3 行为清洗策略（补充实现细节）

明确过滤维度：
- 时间、地点、一次性条件、随机参数 → 标记为 `context_only`（不纳入偏好特征）；
- 工具调用参数中的“长期约束”字段（如 `preferred_format`、`language`、`default_tool`、`cost_limit`）作为候选特征；
- 对话行为指标（可扩展）：
  - `repeat_query_count`：同类查询近 30 天发生次数；
  - `skip_rate`：返回结果被用户跳过的比例；
  - `tool_chain_reuse`：同一工具链连续使用次数。

实现方式：
- 候选特征抽取器（在 `PreferenceExtractor` 之前）：
  - 输入：标准化后的 `MemoryEvent`
  - 输出：`{feature_name: (value, evidence_type)}`，例如 `("preferred_format","markdown","tool_call")`
  - 抽取规则：优先从 `candidate_features` 字段采集，其次从 `content.params` 中根据 `tool_name` 字典映射提取。

- 白名单/黑名单策略实现：
  - 在配置文件中维护 `preference_whitelist` 与 `context_blacklist`，抽取器只输出在白名单内的特征且不在黑名单内的字段。

- 工具参数字典示例（JSON）：
  - `{"file_search": ["result_format","search_scope","sort_order"], "file_export": ["export_format","include_images"]}`

以上算法为可直接实现的伪代码与参数建议，方便把 `DataCleaner`/`DataNormalizer`/`QualityScorer` 转成实际 Python 实现。

## 2. 偏好抽取与隐式偏好生成
### 2.1 规则（显式）偏好抽取 — 具体实现

在 `memoryhub/core/preference/extractor.py` 中实现 `_rule_extract(event: MemoryEvent) -> list[PreferenceMemory]`：

- 输入：标准化后的 `MemoryEvent`（含 `content`、`candidate_features`、`quality_score`）
- 步骤：
  1. 仅对 `event.event_type in {USER_FEEDBACK, MANUAL_CONFIG}` 直接运行规则引擎；
  2. 遍历规则表（从配置或 `rules/*.yaml` 加载）：每条规则包含 `pattern`（正则或模板）、`preference_type`、`extract_template`（如何填充 `content`）、`min_quality`；
  3. 若 `re.match(pattern, event.content.get('text','')) and event.quality_score >= min_quality`，构造 `PreferenceMemory`：
     - `content`：按 `extract_template` 填充（支持 capture groups）；
     - `evidences`：将该 `event` 封装为单条 `Evidence`（带 `polarity='support'`）；
     - `confidence` 初始值：0.9（显式反馈高权重）；
  4. 返回候选列表（按置信度降序）。

示例规则（YAML）：

```yaml
- id: prefer_markdown
  pattern: '(以后|今后).*(用|采用).*markdown'
  preference_type: output_style
  extract_template: '偏好使用 Markdown 输出'
  min_quality: 0.5
```

实现细节：
- 使用 `re.IGNORECASE` 与中文分词预处理（jieba）提高匹配召回；
- 对显式指令增加 `source_weight=1.0`、并在 `Evidence` 中记录 `source_type=USER_FEEDBACK`。

### 2.2 隐式偏好抽取（LLM + 聚合候选）— 具体实现

实现 `_llm_extract(event: MemoryEvent) -> list[PreferenceMemory]`：

- 输入准备：
  1. 确定检索窗口：`window_days = 30`，检索同 `user_id`、同 `scene/task_type` 的 `K=200` 最近事件（按质量和时间排序，优先 `quality_score>=0.6`）；
  2. 构造 `behavior_evidence_pool`：每条证据保留 `event_id, tool_name, params, output_text_snippet, timestamp, source, quality_score, implicit_signals`，将过长文本截断并保留摘要。

- Prompt 与调用参数（可配置）：
  - `model`: 优先 `ollama:qwen2:7b`（本地）或 `openai:gpt-4o-mini`；
  - `temperature`: 0.0~0.3（低温以提高确定性）；
  - `max_tokens`: 512；
  - Few-shot: 提供 3~5 个 `behavior_evidence -> expected JSON` 示例；
  - 输出格式：强制 JSON Schema（`preference_type, scope, content, confidence_factors, reasoning`）。

- Prompt 模板（伪代码）：

```
你是偏好抽取器。给定用户在同一场景下的行为证据列表，请以 JSON 列表返回可能的偏好候选。
证据示例: [{event_id, tool_name, params, output_text_snippet, timestamp, source, quality_score}, ...]
要求: 返回字段 `preference_type, scope, content, confidence_factors, reasoning`。若证据不足，返回空列表或 `insufficient_evidence`。
```

- LLM 输出后处理：
  1. JSON 校验与容错（尝试修正少量语法错误）；
  2. 对每个候选计算 `confidence_factors` 细项：
     - `evidence_count`: 支持该候选的原始事件数；
     - `support_ratio`: 支持事件 / total_evidence_sampled；
     - `recency_score`: 指数衰减加权平均（参考 `confidence` 模型）；
     - `semantic_score`: 将候选 `content` 与支持事件输出向量做余弦平均；
  3. 若 `support_ratio < 0.2 or evidence_count < 2 or confidence_factors.support_ratio < 0.6`，则标记为 `insufficient` 并丢弃。

- 候选去重与合并 `_merge_candidates(candidates)`：
  1. 将候选按 `preference_type + scope` 分组；
  2. 计算 `semantic_similarity`（embedding cosine）在组内阈值 `>0.85` 合并为一条，合并规则：
     - `content` 取主簇最常表达；
     - `evidences` 合并，`evidence_count` 累加；
     - `confidence_factors` 重新计算为加权平均（按证据时间与来源权重）。

伪代码：

```python
def _llm_extract(event):
    pool = retrieve_history(event.user_id, event.scene, event.task_type, days=30, k=200)
    prompt = build_prompt(event, pool, few_shot_examples)
    raw = llm.call(prompt, temperature=0.2, max_tokens=512)
    candidates = parse_json(raw)
    enriched = []
    for c in candidates:
        c['confidence_factors'] = compute_confidence_factors(c, pool)
        if c['confidence_factors']['support_ratio'] >= 0.6 and c['confidence_factors']['evidence_count'] >= 2:
            enriched.append(build_preference_memory(c, evidences_from_pool))
    return _merge_candidates(enriched)
```

### 2.3 弱监督分类器（可选，后期迭代）

当系统积累足够标注（规则抽取 + LLM 输出 + 人工确认）后，可训练一个轻量分类器用于在线快速判断候选是否值得生成偏好：

- 特征工程：
  - 事件级特征：`tool_name, param_key_counts, avg_quality, repeat_count, skip_rate`;
  - 文本特征：`content_length, semantic_embedding`（PCA 降维后）；
  - 时间特征：`recency_gap, session_span`

- 模型建议：
  - 首期：`LightGBM` 或 `LogisticRegression`（快速、可解释）；
  - 训练标签：规则高置信/人工确认为正例，LLM 标注低置信/反对证据为负例；
  - 评估：Precision@K、AUC、F1；阈值优化以保证召回不低于 0.85 时精度最大化。

### 2.4 候选修正与泛化策略

实现 `refine_candidate(candidate, feedback)`：

- 场景一（过细→泛化）：
  - 规则：若 `content` 包含明确工具参数映射（如 `result_format=markdown`）且语义上可抽象，则生成泛化候选：`偏好 Markdown 输出`，并保留原参数作为 `scope.details`。

- 场景二（过宽→收窄）：
  - 规则：若 `candidate.scope` 太宽（`scene='*'`）且支持证据集中在特定 `task_type`，则将 `scope` 收窄为该 `task_type`。

- 自动修正实现：
  - 由 `PreferenceValidator` 提供 `feedback_message`，`PreferenceExtractor.refine_candidate` 根据规则或再次调用 LLM（temperature=0）生成修正版，最多循环 2 次。


## 3. 偏好验证与修正机制

### 3.1 验证器模块

新增 `PreferenceValidator`（建议文件 `memoryhub/core/preference/validator.py`）。验证逻辑包括：
- 证据支持：候选偏好是否基于 `≥2` 条独立事件；
- 抽象质量：是否避免直接复述单条事件；
- 可执行性：是否可映射到后续工具调用参数；
- 时间一致性：是否与最近 `30` 天内的 active 偏好或用户行为一致。

验证器输出：
- `pass` / `weak` / `reject`
- `feedback_message`：如“证据不足”“与当前活跃偏好冲突”“抽象过宽”。

### 3.2 置信度计算：贝叶斯证据驱动模型

现有线性加权方案过于规则化，难以反映“证据支持 vs 证据冲突”的真实动态。建议改为基于“正/反证据权重 + 时间衰减 + 语义一致性”的贝叶斯型置信度。

#### 3.2.1 置信度核心公式

在 `memoryhub/core/preference/confidence.py` 里实现：
- 将每条 `Evidence` 归一化为一个权重 `w_e`，并区分支持型 `s_e` 与反对型 `r_e`。
- `w_e = source_weight * recency_weight * context_match * signal_strength`
- `support_sum = sum(w_e for e in evidences if e.polarity == "support")`
- `oppose_sum = sum(w_e for e in evidences if e.polarity == "oppose")`
- `confidence = sigmoid(logit(prior) + log(1 + support_sum) - log(1 + oppose_sum))`

其中：
- `prior` 可设为 0.5 或基于显式配置/手动标注给出；
- `sigmoid(x) = 1 / (1 + exp(-x))`；
- `log(1 + support_sum)` 使得证据累积呈“递减边际收益”；
- 如果存在大量冲突证据，`oppose_sum` 会快速将置信度压低。

#### 3.2.2 权重设计

- `source_weight`: `explicit_feedback=1.0`, `manual_config=0.95`, `repeated_behavior=0.8`, `tool_call=0.6`, `user_behavior=0.4`
- `recency_weight = exp(-(now - timestamp) / tau)`，建议 `tau = 14 days` 或 `30 days`。
- `context_match`: 当证据 `scope` 与候选偏好当前场景完全匹配时赋值 `1.0`，跨场景弱匹配时 `0.6`，否则 `0.3`。
- `signal_strength`: 根据事件类型区分正向或反向，例如同一工具参数重复出现为 `+1.0`，用户明确反对为 `-1.2`。

#### 3.2.3 一致性与稳定性

- 计算 `cluster_consistency`：将偏好内容按语义相似度聚类，若同一簇占比 `>= 0.7` 则乘以 `1.1`；
- 若存在多簇且主簇支持度较低，则适当降低 `confidence`；
- 通过 `stability_score` 量化“相同偏好是否跨多个会话持续出现”。

#### 3.2.4 证据极性与冲突处理

- `Evidence` 需要明确 `polarity` 字段：`support` / `oppose` / `neutral`。
- 例如：
  - `tool_call` 参数与候选偏好一致 → `support`
  - `user_feedback` 明确反对旧偏好 → `oppose`
  - 不相关的工具结果 → `neutral`
- `update_confidence(preference, new_event)` 应在新增证据时重新计算上述参数，而不是简单线性累加。

#### 3.2.5 置信度分类规则

- `confidence >= 0.8`：长期活跃偏好；
- `0.6 <= confidence < 0.8`：中期偏好，继续观察；
- `0.4 <= confidence < 0.6`：弱偏好，更多证据确认；
- `confidence < 0.4`：暂不保存或标记为 `pending`。

#### 3.2.6 具体实现建议

- `ConfidenceCalculator.calculate(preference)` 读取 `preference.evidences`，批量计算 `support_sum` / `oppose_sum` / `consistency_bonus`。
- `_factor_evidence_count()` 变成“支持证据与反对证据比率的自然对数”；
- `_factor_time_decay()` 使用指数衰减；
- `_factor_consistency()` 评估语义聚合程度并返回 `1.0` ~ `1.2` 的放大系数。

这比简单的线性求和更符合“新证据可逆、冲突证据可消减、时间有记忆”的偏好演进特性。

### 3.3 修正策略

若验证器发现偏好“过细”或“过宽”，对新候选执行：
- 过细：抽取同类偏好后进行泛化，例如把“每次搜索都用`result_format=markdown`”泛化为“偏好 Markdown 输出”；
- 过宽：收窄为“偏好在周报场景下使用 Markdown”，并补充 `scope.task_type`。

实现方式：
- 在 `PreferenceExtractor` 内部增加 `refine_candidate(candidate, validator_feedback)`；
- 若候选内容与场景不匹配，则重新调用 LLM 生成更细粒度结果。

## 4. 差分式偏好版本管理与存储

### 4.1 版本模型落地

当前 `PreferenceMemory` 已支持：
- `version`、`parent_id`、`status`、`created_at`、`updated_at`

建议补充：
- `valid_from`、`valid_to`、`superseded_by` 字段，便于实现“时间有效性账本”；
- `signature` 字段，用于快速判断偏好主键是否相同。

### 4.2 新旧偏好处理规则

在 `PreferenceUpdater` 中实现：
1. 计算候选偏好主键：
   - `signature = sha256(preference_type + scope + normalize(content))`
2. 查找现有 active 偏好：
   - 同 `user_id` + 同 `signature` → 同值更新置信度；
   - 同 `preference_type` + 同 `scope` + 不同 content → 冲突处理；
   - 不同 scope 但 semantic similarity 高 → 合并成更笼统偏好或并存。

### 4.3 差分版本规则

- 同主键同内容：不新增 memory_id，更新 `confidence`、`evidences`、`updated_at`；
- 同主键不同内容：将旧条目 `status=ARCHIVED`、`valid_to=now`、`superseded_by=new_id`；
- 非冲突新偏好：新增 `version=1`；
- 兼容合并：若两个偏好内容互补，可调用 `PreferenceUpdater.merge()`。

### 4.4 版本链与历史回溯

`get_version_chain(memory_id)` 返回从最早版本到当前版本的序列。

这个能力应体现在：
- `GET /api/memory/preferences` 时返回 `parent_id` 和 `version`；
- `GET /api/memory/{memoryId}/versions` 支持历史回放。

## 5. 多维度融合与冲突消解

### 5.1 冲突检测规则

在 `memoryhub/core/conflict/detector.py` 实现：
- 按 `preference_type`、`scope`、`semantic_similarity(content)` 区分：
  - `same type + same scope + content 相反` → 矛盾冲突；
  - `same type +不同 scope` → 可共存；
  - `different type` → 直接共存。
- 相似度衡量：文本嵌入余弦相似度或编辑距离。

### 5.2 决策策略

在 `ConflictResolver` 中实现决策逻辑：
- 如果新候选来自显式反馈或 `confidence > 0.8`，且旧偏好 evidence_weight 显著低，则 `OVERRIDE`；
- 如果内容互补，则 `MERGE`，合并 `content` 与 `evidences`；
- 如果不同子场景且没有本质矛盾，则 `COEXIST`；
- 若冲突不明确，则 `PENDING`，等待用户确认或后续行为验证。

### 5.3 证据融合策略

- 将证据链 `evidences` 合并为“来自 `tool_call` / `user_feedback` / `manual_config`”的加权集合；
- 旧偏好与新偏好同类证据可累积，避免重复写入；
- 通过 `Evidence.weight` 记录时间衰减与来源强度。

## 6. 跨场景适配与冷启动

### 6.1 语义检索优先适配

使用 `memoryhub/retrieval/vector_search.py` + `memoryhub/retrieval/hybrid.py`：
- 将偏好内容向量化并存储到 FAISS；
- 查询新场景时，将 `query = current_task_type + scene + few_shot_context` 与偏好向量匹配；
- 若相似度 `> 0.85`，则将相似偏好作为初始建议。

### 6.2 冷启动方案

- 优先应用显式 `manual_config` 默认值；
- 若无显式配置，则从“用户群体默认偏好模板”初始化；
- 通过 1-2 轮引导对话快速获取核心偏好（如输出格式、工具首选、是否禁止敏感写入）。

### 6.3 跨场景映射原则

- 偏好抽象层级应保持“语义约束”而非“工具参数”；
- 例如“偏好 Markdown 输出”可适配写作、周报、表单生成三类任务；
- “偏好本地检索工具”可适配不同文档搜索场景，但保留 `scope.task_type` 以区分“写作”和“分析”。

## 7. 量化评估与闭环优化

### 7.1 offline 评测指标

在 `evaluation/metrics/preference_eval.py` 中实现：
- 精准率、召回率、F1；
- `evidence_support_rate`：候选偏好由多少独立事件支撑；
- `drift_detection_rate`：最近 30 天偏好变化检测正确率。

### 7.2 online 闭环校验

- 每次偏好实际落地后，观察后续 `tool_call` 是否遵循该偏好；
- 若后续 3 次调用全部违背偏好，则降低该偏好置信度或标记为过时；
- 用户显式纠正立即触发冲突决策。

### 7.3 评估数据来源

- 标注集：`MemoryEvent` → 目标 `PreferenceMemory`；
- 真实流量：工具调用记录与用户反馈。

## 10. 推荐落地逻辑示例

### 事件流

1. OS Agent 完成 `tool_call`，返回 `MemoryEvent`。
2. 预处理后存入事件库；
3. `PreferenceExtractor.extract()` 生成候选偏好；
4. `PreferenceValidator.validate()` 判断 `pass/weak/reject`；
5. `PreferenceUpdater.add()` 写入偏好记忆或触发冲突；
6. `ConflictResolver` 决策后更新活跃偏好；
7. `HybridRetriever` 将偏好与当前任务检索融合，输出给 OS Agent。

### 版本更新场景

- 用户原先偏好“默认使用 Markdown”，后续明确“仅在项目周报使用 Markdown”：
  - 旧偏好 `status=ARCHIVED`，`valid_to=now`；
  - 新偏好 `version=2`，`parent_id=旧偏好ID`；
  - 检索时只返回当前 `ACTIVE` 偏好。

### 冲突处理场景

- 旧偏好“偏好中文回答”，新事件给出“以后用英文写周报”：
  - 语义冲突检测到 `language_preference` 矛盾；
  - 若新事件来自 `user_feedback` 且置信度高，则 `OVERRIDE`；
  - 否则进入 `PENDING`，等待用户确认或后续行为验证。
