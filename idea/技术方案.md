# Kylin-MemoryHub 技术方案

## 面向银河麒麟 OS Agent 的可插拔本地记忆中枢

------

## 1. 项目定位

本项目面向比赛题目 **“OS Agent 记忆优化及高效应用研究”**，目标是设计并实现一个运行在银河麒麟操作系统端侧、可被 OS Agent 调用的可插拔本地记忆中枢。

它不是重新开发一个完整 OS Agent，也不是做一个普通 Web 后端系统，而是做 OS Agent 的 **Memory Subsystem / Memory Plugin / Local Memory Service**。

核心目标是：

> 在 OS Agent 执行任务过程中，为其提供偏好记忆、知识记忆、记忆检索、冲突融合、版本管理、安全过滤、精准遗忘和量化评测能力。

比赛文件明确要求系统支持工具执行结果、用户行为数据、手动配置等多源数据接入，实现偏好动态捕捉、知识结构化整合、端侧轻量部署、敏感信息过滤、自然语言精准遗忘，并满足偏好提取准确率、知识检索召回率、响应延迟、冲突处理正确率等指标要求。

------

# 2. 产品形态

## 2.1 总体产品形态

产品名称建议：

> **Kylin-MemoryHub：面向麒麟 OS Agent 的可插拔本地记忆中枢**

整体关系如下：

```text
银河麒麟 OS
   ↓
OS Agent
   ↓
Memory Adapter 标准记忆接口
   ↓
Kylin-MemoryHub 本地记忆中枢
   ├── 多源数据接入
   ├── 偏好记忆管理
   ├── 知识记忆管理
   ├── 记忆冲突处理
   ├── 高效检索复用
   ├── 安全过滤与精准遗忘
   ├── 本地存储与向量索引
   └── 评测与可视化管理
```

## 2.2 核心边界

### 我们做什么

1. 为 OS Agent 提供记忆能力；
2. 接收 OS Agent 的工具调用结果、用户行为、手动配置；
3. 自动抽取用户偏好；
4. 自动沉淀工作流知识、历史案例、可复用模板；
5. 支持新旧偏好和知识冲突处理；
6. 支持本地高效检索；
7. 支持敏感信息识别和过滤；
8. 支持自然语言精准遗忘；
9. 支持短期、中期、长期记忆流转；
10. 支持量化评测和演示。

### 我们不做什么

1. 不重新做完整 OS Agent；
2. 不把系统定位成云端记忆平台；
3. 不把 Web 后端作为核心产品；
4. 不只做普通 RAG；
5. 不只做简单聊天摘要；
6. 不依赖大型云端模型才能运行。

系统建议分为 7 层。

```text

└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│  2. Memory Adapter 标准接入层                │
│  write / search / update / forget / context │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│  3. Multi-source Ingestion 多源数据接入层     │
│  工具结果、用户行为、手动配置、反馈数据          │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│  4. Memory Core 记忆核心层                   │
│  偏好抽取、知识沉淀、版本管理、冲突融合          │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│  5. Retrieval Engine 高效检索层              │
│  元数据过滤、关键词检索、向量检索、重排序        │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│  6. Local Runtime & Storage 本地运行层        │
│  SQLite、向量索引、缓存、证据库、Embedding SDK │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│  7. Evaluation & Console 评测与展示层         │
│  指标评测、记忆管理、冲突展示、演示报告          │
└────────────────────────────────────────────┘
```

其中真正的核心是：

```text
Memory Adapter
Memory Core
Retrieval Engine
Local Runtime & Storage
```

Console、Web UI、Spring Boot、Vue 等都只是演示和管理手段，不是项目本体。

```text
Java Spring Boot：Memory Service、API、业务编排、Console 后端

SQLite：本地结构化存储
```

## 5.1 OS Agent Simulator

由于比赛阶段大概率拿不到真实麒麟 OS Agent 的完整源码，所以第一版应该先做一个 **OS Agent Simulator**。

它负责模拟真实 OS Agent 的行为：

1. 接收用户任务；
2. 生成任务计划；
3. 模拟工具调用；
4. 产生工具执行结果；
5. 产生用户反馈；
6. 调用 MemoryHub 写入事件；
7. 调用 MemoryHub 检索记忆；
8. 展示记忆增强后的执行结果。

### 示例流程

用户输入：

```text
帮我按上次的方式生成项目周报。
```

Agent Simulator 做：

```text
1. 识别任务类型：office.weekly_report
2. 调用 searchMemory 查询相关记忆
3. 获取历史周报模板、用户偏好、工具链
4. 模拟执行文件检索、日历读取、报告生成
5. 将本次执行结果写入记忆模块
6. 用户反馈后触发偏好更新
```

### 为什么需要 Agent Simulator？

它有三个价值：

1. 让系统可以独立演示；
2. 不依赖真实 OS Agent；
3. 可以证明你的 MemoryHub 是可插拔的。

后期如果有真实 OS Agent，只需要替换 Simulator，MemoryHub 本身不变。

## 5.2 Memory Adapter 标准接口层

Memory Adapter 是“可插拔”的关键。

它向 OS Agent 暴露统一接口，屏蔽底层记忆实现。

### 核心接口

```text
writeEvent(event)
searchMemory(query, context)
getMemoryContext(task)
updateMemory(feedback)
forgetMemory(instruction)
listMemory(filter)
getMemoryVersion(memoryId)
```

### 接口语义

| 接口             | 作用                                       |
| ---------------- | ------------------------------------------ |
| writeEvent       | 写入工具调用、用户反馈、配置变更等事件     |
| searchMemory     | 根据当前任务检索相关偏好、知识、案例、模板 |
| getMemoryContext | 返回可直接拼接进 Agent 上下文的记忆摘要    |
| updateMemory     | 根据用户反馈更新已有记忆                   |
| forgetMemory     | 根据自然语言遗忘指令删除记忆               |
| listMemory       | 展示当前已有记忆                           |
| getMemoryVersion | 查看某条记忆历史版本                       |

### 推荐 API 示例

```http
POST /api/memory/events
POST /api/memory/search
POST /api/memory/context
POST /api/memory/feedback
POST /api/memory/forget
GET  /api/memory/preferences
GET  /api/memory/knowledge
GET  /api/memory/{memoryId}/versions
```

### searchMemory 请求示例

```json
{
  "user_id": "u001",
  "query": "按上次的方式生成项目周报",
  "context": {
    "task_type": "office.weekly_report",
    "app": "os_agent",
    "scene": "office",
    "current_time": "2026-07-08T10:00:00"
  },
  "top_k": 5
}
```

### searchMemory 返回示例

```json
{
  "preferences": [
    {
      "content": "项目周报默认使用 Markdown 格式",
      "confidence": 0.92,
      "scope": "office.weekly_report"
    }
  ],
  "knowledge": [
    {
      "name": "项目周报生成流程",
      "steps": [
        "读取本周日历",
        "检索项目文档",
        "提取完成事项",
        "整理风险问题",
        "生成 Markdown 周报"
      ]
    }
  ],
  "templates": [
    {
      "name": "三段式项目周报模板",
      "sections": ["本周进展", "问题风险", "下周计划"]
    }
  ],
  "latency_ms": 128
}
```

## 5.3 Multi-source Ingestion 多源数据接入模块

比赛明确要求支持工具执行结果、用户行为数据、手动配置信息等统一接入。

### 输入数据源

| 数据源       | 示例                                   | 价值                     |
| ------------ | -------------------------------------- | ------------------------ |
| 工具调用结果 | 文件检索、日历读取、命令执行、报告生成 | 沉淀任务流程和工具偏好   |
| 用户显式反馈 | “以后都用 Markdown”                    | 提取高置信度偏好         |
| 用户行为数据 | 多次修改格式、重复选择某工具           | 提取隐式偏好             |
| 手动配置     | 禁止记忆 API Key、默认输出语言         | 最高优先级约束           |
| 历史任务记录 | 已完成任务轨迹                         | 生成历史案例和工作流知识 |

### 标准化目标

无论输入来自哪里，都统一转成 `MemoryEvent`。

### MemoryEvent 数据结构

```json
{
  "event_id": "ev_001",
  "user_id": "u001",
  "session_id": "sess_001",
  "task_id": "task_001",
  "event_type": "tool_call_result",
  "source": "os_agent",
  "content": {
    "tool_name": "file_search",
    "input": "查找项目周报相关文件",
    "output": "找到 3 个项目文档",
    "status": "success"
  },
  "scene": "office",
  "task_type": "office.weekly_report",
  "timestamp": "2026-07-08T10:30:00",
  "quality_score": 0.86,
  "sensitive_level": "low",
  "metadata": {
    "app": "os_agent",
    "device": "kylin_desktop"
  }
}
```

### 数据清洗逻辑

每条数据进入系统后，经过：

```text
原始事件
   ↓
字段校验
   ↓
去重
   ↓
敏感信息检测
   ↓
质量评分
   ↓
场景识别
   ↓
标准化为 MemoryEvent
   ↓
写入事件库
```

### 数据质量评分

可以定义：

```text
QualityScore =
  0.25 * Completeness
+ 0.25 * SourceReliability
+ 0.20 * ExecutionSuccess
+ 0.20 * UserFeedbackStrength
+ 0.10 * ParseConfidence
```

其中：

| 因子                 | 含义               |
| -------------------- | ------------------ |
| Completeness         | 事件字段是否完整   |
| SourceReliability    | 来源是否可信       |
| ExecutionSuccess     | 工具调用是否成功   |
| UserFeedbackStrength | 是否有明确用户反馈 |
| ParseConfidence      | 系统解析置信度     |

低质量事件只进入短期或中期记忆，不直接进入长期记忆。

## 5.4 Preference Memory 偏好记忆模块

偏好记忆负责回答：

> 用户喜欢什么？习惯什么？在哪些场景下应该怎么响应？

### 偏好类型

| 类型                | 示例                                |
| ------------------- | ----------------------------------- |
| output_style        | 用户喜欢 Markdown、表格、详细解释   |
| tool_preference     | 用户文件任务偏好本地检索工具        |
| workflow_preference | 用户喜欢先列提纲再生成正文          |
| safety_preference   | 用户禁止保存密钥、账号、隐私文件    |
| scene_preference    | 写论文正式，写代码直接，做 PPT 简洁 |
| format_preference   | 周报固定三段式结构                  |
| language_preference | 默认中文回答                        |

### PreferenceMemory 数据结构

```json
{
  "memory_id": "pref_001",
  "user_id": "u001",
  "memory_type": "preference",
  "preference_type": "output_style",
  "content": "项目周报默认使用 Markdown 格式",
  "scope": {
    "scene": "office",
    "task_type": "office.weekly_report",
    "app": "os_agent"
  },
  "confidence": 0.92,
  "status": "active",
  "version": 3,
  "source_events": ["ev_001", "ev_005", "ev_009"],
  "created_at": "2026-07-01T10:00:00",
  "updated_at": "2026-07-08T10:00:00"
}
```

### 偏好抽取流程

```text
MemoryEvent
   ↓
候选偏好识别
   ↓
偏好类型分类
   ↓
场景 Scope 识别
   ↓
证据链绑定
   ↓
置信度计算
   ↓
与已有偏好比对
   ↓
新增 / 更新 / 合并 / 冲突处理
   ↓
写入 PreferenceMemory
```

### 偏好提取方式

第一版不建议直接上复杂模型，可以采用“规则 + LLM/小模型 + 统计”的混合方案。

#### 1. 显式规则抽取

针对用户明确表达：

```text
以后都用 Markdown。
默认生成 PDF。
不要记住我的 API Key。
```

可以用规则模板提取。

示例规则：

```text
以后都用 X → output_style / format_preference
默认使用 X → tool_preference / output_preference
不要记住 X → safety_preference / forget_policy
```

#### 2. 行为统计抽取

例如用户连续 5 次选择 Markdown 输出，就可以提高 Markdown 偏好置信度。

```text
用户反复选择某格式
用户反复修改某类输出
用户反复拒绝某类结果
用户反复使用某工具
```

#### 3. LLM 辅助抽取

对于复杂自然语言反馈，可以使用大模型或本地轻量模型生成候选偏好。

例如输入：

```text
这个太啰嗦了，之后帮我写代码类问题时直接给命令和关键解释就行。
```

抽取：

```json
{
  "preference_type": "output_style",
  "content": "代码类问题回答应简洁，优先给命令和关键解释",
  "scope": "software_development",
  "confidence": 0.89
}
```

### 偏好置信度计算

可以设计：

```text
PreferenceConfidence =
  α * ExplicitScore
+ β * FrequencyScore
+ γ * RecencyScore
+ δ * SuccessScore
+ ε * SourceQuality
- λ * ConflictPenalty
```

建议初始参数：

```text
α = 0.35
β = 0.20
γ = 0.15
δ = 0.15
ε = 0.10
λ = 0.20
```

解释：

| 因子            | 含义                 |
| --------------- | -------------------- |
| ExplicitScore   | 用户是否明确表达     |
| FrequencyScore  | 是否多次出现         |
| RecencyScore    | 是否近期出现         |
| SuccessScore    | 按此偏好执行是否成功 |
| SourceQuality   | 来源数据质量         |
| ConflictPenalty | 是否与旧偏好冲突     |

### 偏好更新策略

```text
如果新偏好与旧偏好相同：
    提高置信度，追加证据

如果新偏好与旧偏好互补：
    合并内容，生成新版本

如果新偏好与旧偏好冲突：
    进入 Conflict Manager

如果新偏好置信度较低：
    暂存为候选偏好，不进入长期记忆
```

## 5.6 Conflict Manager 冲突处理模块

比赛文件明确将知识冲突处理作为核心能力，并给出了知识冲突处理正确率指标。

### 冲突类型

| 类型              | 示例                               | 处理方式       |
| ----------------- | ---------------------------------- | -------------- |
| preference_update | 旧偏好 Markdown，新偏好 Word       | 新版本覆盖     |
| scene_conflict    | 写论文要正式，写代码要简洁         | 按场景并存     |
| safety_conflict   | 用户想记住 API Key，但安全策略禁止 | 安全策略优先   |
| workflow_conflict | 旧流程 3 步，新流程 5 步           | 合并或版本更新 |
| template_conflict | 同类任务多个模板                   | 根据使用率排序 |
| fact_conflict     | 同一知识字段互斥                   | 待确认         |

### 冲突检测逻辑

```text
新记忆进入
   ↓
基于 memory_type + scope 检索相似旧记忆
   ↓
计算语义相似度
   ↓
判断字段是否冲突
   ↓
根据来源、时间、置信度、场景、安全优先级决策
   ↓
覆盖 / 合并 / 并存 / 待确认
```

### 冲突决策优先级

建议规则：

```text
手动配置 > 安全策略 > 用户显式反馈 > 高频近期行为 > 历史行为 > 模型推断
```

### 冲突处理结果

```json
{
  "conflict_id": "conf_001",
  "memory_type": "preference",
  "old_memory_id": "pref_001",
  "new_candidate_id": "cand_009",
  "conflict_type": "preference_update",
  "old_content": "项目周报默认使用 Markdown",
  "new_content": "项目周报默认使用 Word",
  "decision": "override",
  "reason": "用户显式表达新偏好，且场景一致",
  "new_version": 4,
  "created_at": "2026-07-08T11:00:00"
}
```

### 处理策略

| 策略           | 条件                         |
| -------------- | ---------------------------- |
| Override 覆盖  | 同场景、同类型、用户显式更新 |
| Merge 合并     | 内容互补，无强冲突           |
| Coexist 并存   | 场景不同或作用域不同         |
| Confirm 待确认 | 冲突严重，系统无法判断       |
| Reject 拒绝    | 与安全策略冲突               |

## 5.7 Retrieval Engine 高效检索模块

比赛要求知识检索召回率 ≥85%，检索响应时间 ≤500ms。

因此检索模块不能简单做全文搜索，也不能只做向量检索。建议采用混合检索。

### 检索流程

```text
用户当前任务
   ↓
Query 解析
   ↓
场景识别
   ↓
安全策略优先检索
   ↓
元数据过滤
   ↓
关键词检索
   ↓
向量检索
   ↓
结果合并
   ↓
轻量重排序
   ↓
上下文压缩
   ↓
返回 OS Agent
```

### 检索类型

| 记忆类型 | 检索方式                |
| -------- | ----------------------- |
| 偏好记忆 | scope 匹配 + 置信度排序 |
| 知识记忆 | 向量召回 + 标签过滤     |
| 历史案例 | 任务相似度召回          |
| 模板     | task_type 精确匹配      |
| 安全策略 | 强制优先返回            |
| 工具偏好 | 工具类型 + 成功率排序   |

### 检索评分公式

```text
FinalScore =
  0.30 * SemanticScore
+ 0.20 * KeywordScore
+ 0.20 * ScopeScore
+ 0.15 * ConfidenceScore
+ 0.10 * RecencyScore
+ 0.05 * UsageScore
```

其中：

| 因子            | 含义                 |
| --------------- | -------------------- |
| SemanticScore   | 向量语义相似度       |
| KeywordScore    | 关键词匹配度         |
| ScopeScore      | 场景、任务类型匹配度 |
| ConfidenceScore | 记忆置信度           |
| RecencyScore    | 近期程度             |
| UsageScore      | 历史复用次数         |

### 检索性能优化

为满足 500ms，可以采用：

1. 本地向量索引；
2. top-k 控制；
3. 先元数据过滤再向量检索；
4. 热点记忆缓存；
5. 场景级索引分区；
6. embedding 异步生成；
7. 写入和索引更新异步化；
8. 检索结果上下文压缩；
9. 禁止全库扫描；
10. 定期索引压缩。

### 推荐检索链路

```text
Step 1：根据 user_id、scene、task_type 做元数据过滤
Step 2：BM25 / LIKE / FTS 做关键词候选召回
Step 3：HNSW / FAISS 做向量召回
Step 4：合并候选集，去重
Step 5：根据 FinalScore 重排序
Step 6：返回 top-k 记忆
```

## 5.8 Safety & Forget 安全过滤与精准遗忘模块

比赛文件要求集成敏感信息识别与过滤功能，并支持自然语言指令驱动的精准遗忘操作。

### 敏感信息类型

| 类型             | 示例                     |
| ---------------- | ------------------------ |
| credential       | API Key、Token、密码     |
| identity         | 身份证号、手机号、邮箱   |
| file_path        | 敏感本地路径             |
| company_secret   | 公司内部文件名、内部链接 |
| personal_privacy | 私人地址、家庭信息       |
| security_policy  | 权限配置、安全策略       |

### 敏感信息处理方式

| 方式    | 场景                    |
| ------- | ----------------------- |
| reject  | API Key、密码等禁止入库 |
| mask    | 手机号、邮箱等可脱敏    |
| mark    | 可保存但需权限控制      |
| confirm | 不确定内容由用户确认    |
| audit   | 记录处理日志            |

### 入库前安全流程

```text
原始事件
   ↓
正则检测
   ↓
NER / 分类器检测
   ↓
敏感等级判断
   ↓
脱敏 / 拒绝 / 标记
   ↓
写入记忆
```

### 精准遗忘流程

用户输入：

```text
忘掉我关于周报格式的偏好。
```

系统处理：

```text
自然语言指令
   ↓
遗忘意图识别
   ↓
目标记忆定位
   ↓
范围判断
   ↓
执行删除
   ↓
向量索引同步删除
   ↓
缓存失效
   ↓
审计日志
   ↓
返回结果
```

### ForgetOperation 数据结构

```json
{
  "operation_id": "forget_001",
  "user_id": "u001",
  "instruction": "忘掉我关于周报格式的偏好",
  "target_type": "preference",
  "filters": {
    "topic": "weekly_report_format",
    "scope": "office.weekly_report"
  },
  "matched_memory_ids": ["pref_001"],
  "delete_mode": "soft_delete",
  "status": "success",
  "created_at": "2026-07-08T12:00:00"
}
```

### 删除策略

建议第一版使用软删除：

```text
status = deleted
deleted_at = timestamp
delete_reason = user_forget
```

同时：

1. 从向量索引中移除；
2. 清理检索缓存；
3. 不再参与召回；
4. 保留审计记录；
5. 不在普通界面展示。

## 5.9 Memory Lifecycle 记忆生命周期管理

比赛要求方案兼容短期记忆、中期记忆之间的数据流转。

建议设计三层记忆：

| 层级     | 内容                                 | 生命周期        | 存储位置          |
| -------- | ------------------------------------ | --------------- | ----------------- |
| 短期记忆 | 当前会话、当前任务状态、临时工具结果 | 会话级 / 任务级 | 内存 + 临时表     |
| 中期记忆 | 近期任务摘要、候选偏好、近期案例     | 天级 / 周级     | SQLite            |
| 长期记忆 | 稳定偏好、流程知识、模板、历史案例   | 长期            | SQLite + 向量索引 |

### 流转机制

```text
短期记忆
   ↓ 任务完成后总结
中期记忆
   ↓ 多次验证 / 用户确认 / 置信度提升
长期记忆
   ↓ 检索复用
OS Agent 当前任务上下文
```

### 晋升规则

候选偏好进入长期记忆的条件：

```text
满足任一条件：
1. 用户显式确认；
2. 同一偏好出现次数 ≥ 3；
3. 置信度 ≥ 0.85；
4. 在近期任务中反复被成功使用；
```

候选知识进入长期记忆的条件：

```text
满足任一条件：
1. 任务成功完成；
2. 用户给予正反馈；
3. 同类任务多次出现；
4. 工具链稳定；
5. 检索复用后成功率较高；
```

# 14. 最关键的开发原则

## 原则 1：核心模块和展示层解耦

不要让系统变成：

```text
Vue 页面 → Spring Boot Controller → 数据库 CRUD
```

而应该是：

```text
OS Agent / Simulator
   ↓
Memory Adapter
   ↓
Memory Core
   ↓
Memory Store / Retrieval / Safety
```

Console 只是调用 Memory Adapter 的一个客户端。

------

## 原则 2：所有记忆必须有证据链

每条偏好和知识都应该能回答：

1. 它从哪里来？
2. 哪些事件支持它？
3. 置信度是多少？
4. 什么时候产生？
5. 更新过几次？
6. 是否和旧记忆冲突？

这会显著增强答辩说服力。

------

## 原则 3：所有记忆必须有 scope

不要做全局记忆污染。

每条记忆都要有：

```text
scene
task_type
app
user_id
validity
```

否则不同场景偏好会互相干扰。

------

## 原则 4：先规则，后模型

第一版不建议过度依赖大模型。

优先级：

```text
规则抽取 > 统计建模 > 轻量模型 > 大模型增强
```

这样更容易本地部署，也更容易解释。

------

## 原则 5：端侧性能优先

比赛明确要求轻量化端侧部署和 500ms 响应延迟。

所以：

1. 不要每次检索都调用大模型；
2. 不要全库扫描；
3. 不要把所有历史都塞进上下文；
4. 不要依赖云端 embedding；
5. 不要把复杂推理放在实时检索链路里。

------

# 15. 技术亮点包装

答辩时可以把技术亮点总结成 4 个。

## 亮点 1：基于证据链的偏好动态捕捉

不是简单保存用户说过的话，而是结合：

```text
显式反馈
行为频次
最近性
工具执行结果
数据质量
冲突惩罚
```

动态计算偏好置信度。

## 亮点 2：场景作用域驱动的记忆版本管理

每条记忆都有 scope，支持：

```text
同场景覆盖
不同场景并存
历史版本回溯
证据链追踪
```

## 亮点 3：面向端侧的混合检索引擎

采用：

```text
元数据过滤 + 关键词召回 + 向量召回 + 轻量重排序 + 缓存
```

在保证召回率的同时控制响应延迟。

## 亮点 4：自然语言精准遗忘与安全治理

支持：

```text
敏感信息入库前检测
自然语言遗忘解析
结构化记忆删除
向量索引同步删除
缓存失效
审计追踪
```
