## 二、LLM 服务配置：来源澄清与密钥归位

### 背景

桌面端「LLM 服务配置」页保存后重启不生效，且保存返回 `409 llm.config_file_unavailable`。

### 结论

配置优先级为 **进程环境变量 > `.env` > `config.yaml` > 代码默认值**
（`memoryhub/config.py:668-812`）。仓库根 `.env` 里的 `LLM_API_BASE` / `LLM_MODEL`
会盖掉 `config.yaml`，使页面保存对 base/model 失效。

`409 llm.config_file_unavailable` 的唯一触发点（`memoryhub/adapter/api.py:417-419`）是
服务进程没有可写的 `config.yaml`（cwd 下无该文件，或 `MEMORYHUB_CONFIG` 指向不存在的路径）。
已本地复现并确认：从仓库根启动的后端返回 200，从无 `config.yaml` 的目录启动返回 409。

### 改动

| 文件 | 改动 |
|---|---|
| `.env`（本地，gitignore） | 注释掉 `LLM_API_BASE` / `LLM_MODEL`；`LLM_API_KEY` 存放真实密钥 |
| `config.yaml` | `llm.api_key` 留空（密钥不进 git）；保留 deepseek 的 `api_base` / `model` |
| `.env.example` | 同样注释掉这两项并补充说明，避免 `cp .env.example .env` 重新踩坑 |

分工：**`api_base` / `model` 由 `config.yaml` 与页面管理；密钥只放 `.env`**（`.env` 被 gitignore 忽略）。
代价：之后在页面改密钥不会生效（`.env` 优先），需同步改 `.env`；已在 `.env` 内注明。

## 三、MCP 检索失败修复

### 根因（两个独立缺陷，均为静默 `200 + total_count=0`）

**A. tenant 默认值读写不一致**
- 写入：`api.py:531` 原为 `tenant_id = headers.get("X-MemoryHub-Tenant", event.user_id or "default")` → 无 header 时取**用户 ID**；
- 检索：`api.py:1174/1225` 无 header 时取 **`"default"`**。
- 后果：经 vNext 权威链路形成的记忆投影出 `tenant_id=<用户名>`，检索请求为 `default`，
  在 `retrieval_executor.py:164-166` 被静默丢弃（`candidate_count=0`）。
- OpenCode 插件正是无 header 直连 `/api/memory/events`（`memoryhub.plugin.mjs:46`）。

**B. MCP 把 `context.app` 当作用域选择器**
- `memoryhub_mcp/tools.py:63` 硬编码 `app="memoryhub-mcp"`，且 `scene` / `task_type` 无兜底；
- 经 `_legacy_scope_to_vnext`（`vnext_schemas.py:460-473`）映射为 `APPLICATION:memoryhub-mcp`，
  与记忆实际的 `TASK:coding_task` 不匹配，在 `retrieval_executor.py:644-650` 被丢弃。

### 改动

| 文件 | 改动 |
|---|---|
| `memoryhub/adapter/api.py:531` | 租户缺省值改为 `"default"`，与其余端点（`api.py:1174/1225`、`agent_api.py:241/264/321`）对齐 |
| `agent-integration/memoryhub_client/client.py` | `MemoryHubClient` 新增可选 `tenant_id`，`search` / `get_context` 带上 `X-MemoryHub-Tenant` |
| `agent-integration/memoryhub_mcp/server.py`、`memoryhub_cli/cli.py` | 传入 `config.tenant_id` |
| `agent-integration/memoryhub_mcp/tools.py:63` | 去掉硬编码 `app`，检索默认不带任何作用域（仅调用方显式传 `scene`/`task_type` 时才带） |

### 验证

- 单元级：`metadata.tenant_id=lcz` 时，`tenant_id="default"` 的转换返回 `None`，`tenant_id="lcz"` 返回 `RetrievedMemory`。
- 接口级：`X-MemoryHub-Tenant: claudecode` → `total=0`；`default` → 命中。

## 四、冲突处理：分析结论与三批修复

### 分析结论（写入 → 检索 → 演化）

| 时刻 | 实现 | 决策 |
|---|---|---|
| 写入 | `core/preference/updater.py`、`core/knowledge/updater.py` | override / merge / coexist / pending |
| 检索 | `retrieval/scope_resolver.py` | 按 identity_key 分组 + 作用域优先级（TASK > PROJECT > APPLICATION > DOMAIN > GLOBAL > SESSION） |
| 演化 | `domain/evolution.py` + `application/evolution_service.py` | REINFORCE / REVISE / SUPERSEDE / COEXIST / REVIEW |

关键事实：**vNext 主链路不写 `ConflictRecord`**（`memoryhub/application/` 下无 `conflict_repo.save`），
它走 `EvolutionAction.REVIEW/COEXIST`；冲突中心只反映 legacy 抽取链路。

### 第一期：bug 修复

| 编号 | 文件 | 问题 | 修复 |
|---|---|---|---|
| F1 | `desktop-client/src/pages/ConflictPage.cpp` | 服务端 `total` 被本页条数覆盖 → 翻不到第 2 页 | 仅"已解决"全量视图用可见条数，分页视图保留服务端 total |
| F2 | 同上 | "事实"筛选项永远为空（无 `memory_type="fact"` 的冲突记录） | 删除该选项 |
| F3 | 同上 | 类型筛选只过滤本页，但文案写"共 N 条" | 标注"本页筛选后 N 条" |
| F4 | `memoryhub/adapter/api.py` | `resolve` 的 `decision` 不校验，脏值可落库 | 入口用 `ConflictDecision` 校验，非法值 → 400 |
| F5 | `memoryhub/core/preference/updater.py` | 偏好冲突 `conflict_id` 每次随机 → 重复冲突对产生多行 | 改为确定性 `conf_pref_{sha256(user\|old\|new)[:24]}`，与知识侧对齐 |

附带：冲突卡片补只读记忆 ID；副标题改为"裁决仅记录结论"；`docs/architecture.md:88` 修正冲突矩阵的
真实位置并注明 `core/conflict/` 仅被测试引用；`core/conflict/{detector,resolver}.py` 头部加注说明。

### 第二期：服务端过滤（F6 / F7）

`GET /api/memory/conflicts` 新增（缺省行为不变）：

- `status=resolved`：等价于 `decision != pending`（库中无 `resolved` 值）；
- `memory_type`：按 `preference` / `knowledge` 过滤。

前端冲突页改为**服务端过滤 + 服务端分页**：状态与类型切换均重新请求，删除本地过滤
（`applyLocalView` / `m_cachedItems`），"已解决"视图不再全量拉取。

### 第三期：裁决落地（F8 / F9）

`POST /api/memory/conflicts/{id}/resolve` 新增 `apply: bool = False`（默认仍只记录结论）：

| 决策 | `apply=true` 的行为 |
|---|---|
| `override` | 归档旧记忆 → 生成带版本链的后继（`parent_id`/`root_id`/`version+1`、证据合并） |
| `merge` | 归档旧记忆 → 生成合并版本 |
| `coexist` | 两条均置 ACTIVE（PENDING 的新记忆被激活） |
| `pending` | 400 `conflict.cannot_apply_pending` |

守卫：记忆缺失 → 409 `conflict.memory_missing`；非本人 → 403 `conflict.owner_mismatch`；
写入统一经 `memory_write_service`（过安全门禁），异常收敛为 409 `conflict.apply_failed`。

接线时补了两处此前缺失的语义（`core/conflict/resolver.py`）：
`apply_merge` 原本不归档旧记忆（合并后新旧同时 ACTIVE）、`apply_coexist` 原本不激活 PENDING 新记忆。

前端裁决弹窗新增默认不勾选的「同时应用到记忆」复选框，勾选才发送 `apply: true`。

F9 以文档形式落地：`docs/api.md`、`desktop-client/README.md` 与页面空状态均说明
"冲突中心只覆盖 legacy 链路，vNext 冲突以 REVIEW 状态出现在偏好/知识页待审队列"。
