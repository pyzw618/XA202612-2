# MemoryHub 四项指标测评报告

> 证据等级：**LIVE_HTTP**（全部数据由 HTTP 端到端采集自已部署的真机服务）
> 目标平台：银河麒麟桌面操作系统 V11 x86_64
> 对应赛题指标：偏好提取准确率 ≥85%、知识检索召回率 ≥85%、知识检索响应时间 ≤500ms、知识冲突处理正确率 ≥88%

---

|---|---:|---:|---:|---|

## 2. 测评方法

### 2.1 三条基本评测原则

**（1）只测真机，不测进程内实现。**
评测客户端（`evaluation/live/`）**不 import `memoryhub.*` 运行时对象**，只通过 HTTP
访问已部署服务。原因是仓库内的 `config.yaml` 是 `mock` + `faiss`，而实际交付运行的
是麒麟 embedding SDK + Milvus；若走进程内路径，测出来的是另一套系统。

每次检索响应都断言 `served == "vnext"`，不符即中止。这用于排除内置的
`POST /evaluate/{retrieval,latency}` 端点在正式数字中的使用——它们走的是 legacy
`app.state.retriever`，且偏好/冲突评估器以 `llm_client=None` 构造（只测规则路径）。

**（2）标签来自规格，不来自被测实现。**
数据集每条样本携带 `label_source`，指向定义该期望的规格条款。加载时机械拒绝以
`observed:` / `live:` / `predicted:` 开头的标签——那类标签是抄系统输出得来的，
测出来必然满分，属循环自证。

反例（旧 showcase 数据集）：`expected_output` 被硬编码为规则抽取器的固定输出字符串
（"偏好使用 MARKDOWN 格式进行数据输出。"），指标恒为 100%，该数字无意义。

**（3）判定采用三态，未测量不等于通过、也不等于 0 分。**
无法测量的指标记为"未测量"。冲突评测中的 `drive_failure`（偏好对未能被关联）单独
统计，不混入决策正确率。

### 2.2 四项指标的口径定义

| 指标 | 计算口径 |
|---|---|
| 偏好提取准确率 | 四字段全对比例：`preference_type` + 归一化 `payload.target` + 归一化 `payload.value` + `is_global`（三态，可为"不作断言"）。文本相似度仅作诊断字段，**不参与判分**——避免同义改写被误判为失败。 |
| 知识检索召回率 | `Recall@5 = 命中数 / |relevant|`，`relevant = 相关性等级 ≥ 2`。v2 数据集每条查询**恰有一个**等级 3 目标记忆，因此等价于"目标是否落进 top-5"。retrieved 侧保序去重；`no_answer` 查询不入分母，单独计 `no_answer_precision`。 |
| 知识检索响应时间 | 取 **并发 1、cold 阶段**的**客户端端到端**耗时 P95，**含** embedding 调用与网络往返。服务端自计 `latency_ms` 并列报告作为支撑。cold 阶段每条查询文本唯一，同时绕过查询向量缓存与结果缓存。 |
| 知识冲突处理正确率 | **端到端口径**：正确决策数 / 全部用例数（未能关联的偏好对计为未正确处理）。另附"条件正确率"（仅在成功关联的样本上计算），用于定位关联之后的决策质量。 |

### 2.3 语料就绪判定（三段信号）

生产模式下写入只落 projection outbox，向量投影由后台 worker 完成，因此"接口返回
200"不等于"记忆可被检索"。评测在计分前执行三段就绪判定，任一不满足即中止（退出码 4）
而不记录低分：

1. **outbox 排空** —— `GET /api/memory/v2/projections` 无 pending/failed；
2. **reconcile 无漂移** —— `POST /api/memory/admin/reconcile` 返回 `still_pending=0`；
3. **canary 可检索** —— 抽样 20 条已播种记忆，用其**名称**做无 scope 检索，
   要求 `recall@5 ≥ 0.95` 且**无 0 结果查询**。

第三项是区分"排序质量差"与"索引根本没建"的唯一信号。无 canary 时，索引故障导致的
低召回会被误读成模型效果不佳。

### 2.4 前置条件告警

环境指纹会检查会让某项指标失去意义的前置条件并写入报告。例如 LLM 密钥未配置时，
`PreferenceExtractor._llm_extract` 直接返回空，隐式偏好一条都抽不出来——此时偏好
准确率只反映规则覆盖度。该告警避免读者把配置缺失误读成算法不行。

## 3. 测试流程

### 3.1 前置门

```bash
curl -s http://127.0.0.1:8099/api/memory/system/status | python3 -m json.tool
```

断言：`runtime_mode=production`、`embedding.provider=kylin`、`embedding.dimension=768`、
`vector_engine.provider=milvus`、`connected=true`、`retrieval.type=MilvusHybridRetriever`。
不满足时以退出码 2 中止。

### 3.2 执行

```bash
.venv/bin/python -m evaluation.runners.run_live_four_metrics \
  --base-url http://127.0.0.1:8099 --top-k 5 \
  --concurrency 1,4,8,16 --warmup 100 \
  --output-json evaluation/results/live/four_metrics_<UTC>.json \
  --output-md   evaluation/results/live/four_metrics_<UTC>.md
```

| 退出码 | 含义 |
|---:|---|
| 0 | 四项全部测量完成 |
| 2 | 环境指纹不满足验收要求 |
| 3 | 服务不可达 |
| 4 | 语料就绪判定失败（索引故障，分数无意义） |
| 5 | 播种超时 |

检索评测的完整子流程：

1. **身份隔离**：每次运行生成唯一 `user_id`（`evalrun_<UTC>_<rand4>`），并被烘焙进
   memory_id 与 project_id。引擎的标量过滤只认 `user_id`/`status`，唯一用户名天然
   杜绝跨运行与真实数据串扰。
2. **播种**：逐条 `POST /api/memory/memories/knowledge`，并发 8，失败重试（安全门
   扫描出错时会回退到 `review_required`，属瞬时抖动）。
3. **就绪判定**：见 §2.3。
4. **计分**：`scoped`（携带 context + project_id，生产真实路径）与 `unscoped`
   （不带 scope，观测纯排序能力）各跑一遍。

### 3.3 结果读取的校验点

| 校验 | 目的 |
|---|---|
| 每次响应 `served=vnext` | 证明数字来自 vNext 链路而非 legacy |
| canary 20/20 且零结果=0 | 证明语料确实可检索 |
| 数据集 SHA256 校验 | 证明用的是冻结版本，跨轮次可比 |
| 请求留痕（次数、状态码、served 观测值） | 证明数据确实来自真机 |

## 4. 测试集情况

### 4.1 清单与溯源

| 数据集 | 规模 | 用途 | SHA256（前 16 位） | label_source |
|---|---|---|---|---|
| `memoryhub_graded_retrieval_v2.1_dev.json` | 600 记忆 / 120 查询 | 检索召回 | `b029d7875f5a70a3` | `spec:graded-retrieval-v2.1#relevance-grading` |
| `memoryhub_preference_extraction_v2.1.json` | 240 样本 | 偏好提取 | `32bff1fb3b52756c` | `spec:preference-extraction-v2.1#blocks` |
| `memoryhub_conflict_resolution_v2.1.json` | 180 样本 | 冲突处理 | `7d089fdac2a60a84` | `spec:conflict-resolution-v2.1#decision-matrix` |
| `memoryhub_retrieval_latency_v2.1_dev.json` | 100 预热 + 2000 正式 | 响应时间 | `c7b25fef9f2e4959` | `spec:latency-v2.1#unique-query-only` |
| `memoryhub_graded_retrieval_v2.1_test.json` | 1980 记忆 / 396 查询 | 大规模检索 | `7a7c374041e202dd` | 同上 |

全部数据集由 `evaluation/datasets/generators/` 下的生成器**确定性**产出
（固定 seed、固定 `created_at`），同一组参数逐字节可复现；完整性由
`evaluation/datasets/SHA256SUMS.txt` 冻结。

**注意 `label_source` 一栏**：它是区分数集合规性的关键字段，加载器会拒绝
`observed:` 前缀的标签。

### 4.2 检索数据集（600 记忆 / 120 查询）

**领域**：办公 / 开发 / 运维 / 项目管理 / 个人偏好 / 安全合规，每域 10 个任务词。

**记忆构成**（每个任务 10 条）：

| 类型 | 条数 | 角色 |
|---|---:|---|
| `workflow` | 1 | 目标记忆（唯一等级 3） |
| `case` / `template` | 2 | 同主题其他知识类型（等级 1） |
| `xproj` 跨项目探针 | 1 | 主题相关但**属于别的项目**，用于隔离检查 |
| 同主题填料 | 6 | 侧面笔记（注意事项/常见问题/工具选型/时效要求/口径说明/失败案例），等级 1 |

共 600 条：`workflow 240 / case 180 / template 180`。

**查询分档**（每档 24 条，共 120）：

| 难度 | 构造方式 | 考查点 |
|---|---|---|
| `exact` | 含任务词与流程线索，如"帮我生成项目周报，走哪套流程" | 精确词面匹配 |
| `paraphrase` | 用任务目标改写，不复述任务词 | 同义改写 |
| `semantic` | 用产出物表述，如"结构化周报要怎么做才能既快又不出错" | 语义匹配 |
| `cross_scope` | 指向**另一个项目**的同主题探针 | scope 隔离与召回 |
| `no_answer` | 语料中无对应记忆 | 不该返回结果时的表现 |

**相关性分级规则**：目标记忆 = 3；同主题、同 scope 的侧面记忆 = 1。
**刻意不产生等级 2**——语料中不存在"同样完整可替代"的第二条记忆，硬造一个会让
召回变成"两条都得命中"才算满分，与"召回率"的直观口径不符。

**三条设计约束**（均由生成器机械校验，违反即构建失败）：

1. **查询不得泄漏目标标题**：查询文本不得包含目标记忆 `name`，也不得包含其长度
   ≥6 字的连续子串。（v1 数据集的查询大量直接复制标题，导致召回虚高。）
2. **scope 从目标记忆复制**：v1 有 214 条 `task_type` 与 115 条 `project_id` 失配，
   使"相关记忆"在严格 scope 门下根本不可达，召回上限被压到约 0.65。
3. **干扰项不得比正例更贴合查询**：填料正文不复述主题词。早期版本让填料重复
   "{phrase}"，导致其与查询的词面重叠高于正例本身（正例一度排名垫底）。

**越界项单独标注**：`scope_blocked` 字段记录"主题相关但确实越界"的记忆，共 96 条。
它们不进召回分母；若被系统返回则计入 `isolation_violation_rate`。这样"排序没排上"
与"隔离正确挡掉"是两个分开的、诚实的数字。

### 4.3 偏好提取数据集（240 样本）

| 块 | 条数 | 说明 |
|---|---:|---|
| `rule_hit` | 100 | 规则触发词明确（格式偏好 70 + 隐私约束 30），预期走规则路径 |
| `llm_required` | 100 | **不含**任何规则触发词的隐式偏好，必须由 LLM 抽取 |
| `hard_negative` | 40 | 客观事实、一次性指令、疑问句等，**正确行为是不产出偏好** |

生成器内置与抽取器等价的两条规则判据，构建时断言 `rule_hit` 必然命中、
`llm_required` 与 `hard_negative` 必然不命中——分类写错在生成阶段即失败。

`rule_hit` 衡量规则覆盖度，`llm_required` 才是 LLM 路径的真实能力，二者分开报告。

### 4.4 冲突处理数据集（180 样本）

| 块 | 条数 | 期望行为 | 标签依据 |
|---|---:|---|---|
| `preference_native` | 120 | 同 scope 同 target、值相同 → `merge`；值不同且新偏好来自显式反馈 → `override` | `ConflictResolver.auto_resolve` 决策矩阵 |
| `coexist` | 30 | scope 不同且均非全局 → 两条偏好**并存且不产生冲突记录** | 同上（该分支 `_find_existing` 返回空，直接落库） |
| `llm_required` | 30 | 同义改写（"都用 markdown 格式" vs "输出请保持 markdown 排版"），语义等价 → `merge` | 需 LLM 抽取才能形成可比偏好 |

**必须经事件链路驱动**：`POST /api/memory/memories/preference` 直接落库、
**不触发** `PreferenceUpdater`，永不产生冲突记录（已实测：连写两条同 target、
不同值的偏好，两条都 active 且冲突表为空）。冲突只在 `/api/agent/step` 的事件
抽取链路上产生，因此每条用例需对同一用户连续写两次。

### 4.5 延迟查询集（100 预热 + 2000 正式）

对数据集的硬要求是**查询文本全局唯一**：`cold` 阶段必须在查询向量缓存与结果缓存上
同时落空，重复文本会把延迟测成"缓存命中时间"。生成器用"任务词 × 前缀 × 后缀"
组合保证 2100 条文本互不相同。本数据集**不提供相关性标注**——只测耗时，不测排序。

## 5. 测试结果

### 5.1 知识检索召回率

**总表**：scoped `Recall@5 = 91.67%`、`MRR = 0.7599`、`NDCG@5 = 0.9004`；
`isolation_violation_count = 0`（无越界泄漏）。
对照：unscoped `Recall@5 = 81.25%`。

**分难度**：

| 难度 | 条数 | Recall@5 | MRR | NDCG@5 |
|---|---:|---:|---:|---:|
| exact | 24 | **1.00** | 1.0000 | 0.9916 |
| paraphrase | 24 | **1.00** | 0.7625 | 0.9068 |
| cross_scope | 24 | **1.00** | 0.9583 | 0.9692 |
| semantic | 24 | 0.6667 | 0.3188 | 0.7340 |

**两点值得注意**：

- **scoped（91.67%）高于 unscoped（81.25%）**：scope 门把候选收敛到正确任务域后，
  排序反而更准。这说明隔离机制不仅保证安全，也有助于精度。
- **semantic 档（66.67%）是唯一短板**：该档查询与目标往往**没有词面交集**，
  词面重排信号失效，只能退回稠密通道。

`no_answer_precision = 0.1667`：系统对无答案查询几乎总会返回结果，缺少相关性
阈值过滤。这是已知短板，不影响召回率口径（no_answer 不入分母）。

### 5.2 偏好提取准确率

**总表**：`accuracy = 87.50%`（240 例四字段全对 210 例）。

| 块 | 条数 | 准确率 | 说明 |
|---|---:|---:|---|
| rule_hit | 100 | **99.00%** | 规则覆盖度 |
| llm_required | 100 | **86.00%** | LLM 隐式抽取的真实能力 |
| hard_negative | 40 | 62.50% | 15 例被误抽为偏好（均来自 LLM 的 `implicit_inference`） |

**按偏好类型**：

| 类型 | 条数 | 准确率 |
|---|---:|---:|
| format_preference | 70 | 100.00% |
| language_preference | 16 | 100.00% |
| safety_preference | 30 | 96.67% |
| workflow_preference | 24 | 91.67% |
| scene_preference | 16 | 87.50% |
| tool_preference | 20 | 85.00% |
| output_style | 28 | 71.43% |
| （hard_negative） | 40 | 62.50% |

**关键发现**：LLM 密钥配置前后，本指标为 **61.25% → 87.50%**。未配置密钥时
`_llm_extract` 直接返回空，100 例隐式偏好中 93 例完全抽不出、3 例被归为知识记忆，
缺口**完全来自配置缺失而非算法**。该前置条件已加入环境指纹自动告警。

**已知短板**：`hard_negative` 的 62.50% 表明 LLM 对"客观事实 / 一次性指令"存在
过度抽取倾向（15/40）。这是当前最值得优化的方向。

评测走真实写入链路（`POST /api/agent/step`），每例使用独立身份——同一用户下
后续偏好会命中冲突/合并机制，`preferences_written` 返回空，样本会被误判为"未抽取"
（实测同一用户连写 4 条规则命中样本只有第 1 条上报）。

### 5.3 知识冲突处理正确率

**总表**：端到端 `accuracy = 91.67%`（165/180）；条件正确率 100%（165/165）。

| 块 | 条数 | 成功关联 | 未关联 | 端到端正确率 | 条件正确率 |
|---|---:|---:|---:|---:|---:|
| preference_native | 120 | 120 | 0 | **100%** | 100% |
| coexist | 30 | 30 | 0 | **100%** | 100% |
| llm_required | 30 | 15 | 15 | 50% | 100% |
| **合计** | **180** | **165** | **15** | **91.67%** | 100% |

**口径说明**：两个数字回答不同问题——端到端衡量"系统最终有没有正确处置这对偏好"，
条件值衡量"关联上之后的决策矩阵是否正确"。本报告以端到端为 headline。

**15 例未关联的成因**：新旧偏好**都写入成功**（`old_written=new_written=true`）、
两条偏好**并存为 active**，但系统**没把它们识别为一对**——即 `_find_existing` 的
目标匹配未命中同义改写。这是真实的功能缺口，属"知识冲突处理正确率"扣分项。

**该指标曾完全无法测量**：服务端有两个主键碰撞缺陷（详见 §8），而冲突评测按定义
就要对同一用户写第二次，正好命中——表现为事件写入整条丢弃、抽取完全不执行。

### 5.4 知识检索响应时间

**并发曲线**（客户端端到端，含 embedding 与网络）：

| 阶段 | 样本 | P50 | P95 | P99 | Max | 错误 |
|---|---:|---:|---:|---:|---:|---:|
| cold_c1 | 500 | 54.8 | **73.1** | 95.9 | 228.3 | 0 |
| cold_c4 | 500 | 204.0 | 233.8 | 257.2 | 402.2 | 0 |
| cold_c8 | 500 | 409.3 | 471.9 | 794.7 | 882.0 | 0 |
| cold_c16 | 500 | 841.3 | 1009.6 | 1161.3 | 3510.8 | 0 |
| vector_hot_c1 | 50 | 51.8 | 67.9 | 73.8 | 74.1 | 0 |

`cold_start_first_request_ms = 40.31`。

**口径声明**：≤500ms 的结论取 **cold_c1（并发 1）**。这是桌面 OS Agent 的真实
使用形态——单用户交互式检索。并发档位一并公布，供读者判断容量边界。

**容量特征**：吞吐量在各并发档均约 20 QPS 不随并发增长；服务端自计延迟恒定在
约 40ms 不随并发变化，而客户端延迟随并发线性增长。说明瓶颈在请求排队而非服务端
处理。**服务端计时器为何未包含排队时间，现有数据无法解释，需进一步埋点确认。**

## 7. 已知局限

1. **semantic 档召回 66.67%**：查询与目标无词面交集时，当前词面重排失效，只能
   退回稠密通道。进一步改善需语义重排器，其代价（+1~2s）与 ≤500ms 的延迟指标
   互斥，属产品取舍。
2. **no_answer 精确率 16.67%**：系统缺少相关性阈值，对无答案查询几乎总会返回结果。
3. **hard_negative 准确率 62.50%**：LLM 对客观事实/一次性指令存在过度抽取倾向。
4. **llm_required 冲突块 50% 未关联**：同义改写的目标匹配能力不足。
5. **并发扩展性**：吞吐约 20 QPS 平台期，高并发下延迟线性增长；瓶颈定位需进一步
   埋点。
6. **数据集为合成数据**：领域词表与查询模板由人工设计，虽已消除标题泄漏、scope
   失配与干扰项词面压制三类构造缺陷，仍与真实用户语料分布存在差距。
7. **检索与延迟、偏好与冲突分两批测量**：均为同一服务实例、同一代码版本，检索与
   延迟为最终版本所测，偏好与冲突为 LLM 密钥配置后所测。

## 8. 附：测评过程中发现并修复的产品缺陷

测评本身暴露了若干必须修复才能测出真实数字的缺陷，均已在 `docs/retrieval-recall-findings.md`
与代码注释中留档。

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | `working_state_id` 由 tenant/user/task 拼接后硬截断到 64 字符 | 长 user_id 下 task_id 被整段截掉，**同用户第二个任务撞主键**，事件写入整条丢弃 |
| 2 | `episode_id` 只由 task_id 派生、**不含用户** | **任意两个用户任务重名即碰撞**，写入失败、抽取不执行 |
| 3 | `.env` 中的空值覆盖配置文件有效值 | 生产下 Milvus 连接参数被清空 |
| 4 | `_metadata_store` 只在 insert 时填充、无启动回填 | **服务重启后标量过滤滤空一切**，检索表现为"服务正常但返回 0 条" |
| 5 | `pending_index` 在投影完成前被清 0 | 投影漂移不可见、无人重试 |
| 6 | 服务配置以 `root:0644` 安装 | 桌面端「LLM 服务配置」保存必然失败（`llm.config_persist_failed`） |
| 7 | `Reranker` 相关性打分按空格分词 | 中文查询只得 1 个 token，打分失去分辨率 |
| 8 | `VNextReranker` 相关性打分按空格分词（**生产路径上真正生效的那个**） | 占权重 0.20 的"相关性"对中文恒为常量，**重排形同虚设**，召回被压在 64.58% |

**缺陷 8 是召回率的关键**：修复后 `Recall@5` 由 72.92% 提升到 **91.67%**，
且延迟无变化（75.27ms vs 81.89ms）。

**方法论教训**：本轮多次判断被实测推翻，根因是**对调用链的假设未经核实**——请求由
vNext `RetrievalService` 服务，`MilvusHybridRetriever` 只是其 `vector` 通道之一，
最终排序实际发生在 `VNextReranker`。先确认"哪段代码真正决定结果"，再动手。
