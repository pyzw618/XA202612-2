> 本文基于项目**实际代码、配置、目录与文档**系统梳理而成。凡结论均标注代码/文件依据（`文件:行号`）；当 README/文档与代码不一致时，**以代码为准**并显式指出差异；无法确认之处标注「推测 / 无法确认 / 待进一步验证」。

## 1. 一句话介绍

**Kylin MemoryHub 是面向银河麒麟（Kylin）OS Agent 的本地化「记忆系统 / 记忆引擎」**：负责 Agent 运行过程中的**偏好、知识、事实类记忆**的抽取、存储、检索、遗忘与全生命周期管理，并提供 CLI / MCP / OpenCode / Qt 桌面 / Python SDK 多种接入方式。

---

## 2. 整体介绍

- **项目定位**：赛题编号 `XA-202612`，由麒麟软件发榜「OS Agent 记忆优化及高效应用研究」（依据 `docs/赛题要求.md`）。MemoryHub 是该赛题的参赛/交付工程，目标是为 OS 级 Agent 提供一套**可本地部署、安全可控、可灰度演进**的记忆能力底座。
- **核心能力**：记忆的「写入 → 抽取 → 存储 → 检索 → 遗忘 → 生命周期」闭环；内置**安全门禁**（敏感信息检测、隔离区加密、审计链）、**灰度发布**（vNext 新架构可灰度、可回滚、双读对比）。
- **关键事实（代码确认）**：项目并非单一架构，而是**双层架构并存**——
  - **Legacy 层**：`memoryhub/core/`（记忆写入、事件摄取、偏好/知识抽取、安全）＋`memoryhub/retrieval/`（检索引擎）。
  - **vNext 层**：`memoryhub/application/`（canonical 写入编排、检索服务、事件网关、灰度、遗忘）+ `memoryhub/domain/`（vNext 领域词汇表/契约）。
  - README **未充分描述 vNext 层**，这是文档与实现最显著的差距（见第 12 节）。
- **运行形态**：FastAPI 服务（组合根 `memoryhub/app.py:create_app()`，默认监听 `127.0.0.1:8099`），SQLite 作为事实源，向量引擎在生产用 Milvus、开发用 FAISS+BM25 降级。

## 6. 系统架构

整体是**「组合根 + 分层 + 灰度双轨」**结构：

```
                        接入层 (agent-integration / desktop-client / CLI / MCP / OpenCode)
                                       │  HTTP  (127.0.0.1:8099)
                                       ▼
                        memoryhub/adapter  (5 个 router: api / vnext_api / agent_api / memory_v2_api / management_api)
                                       │
                  ┌────────────────────┴─────────────────────┐
            【vNext 写入/检索主轨】                      【Legacy 写入/检索轨】
   application/canonical_write + event_gateway      core/ingestion + core/memory_write
   application/retrieval_service                    retrieval/* (hybrid/milvus/reranker)
   application/formation_worker                     core/preference + core/knowledge
   application/forget_service
                  └────────────────────┬─────────────────────┘
                                       ▼
                  安全门禁 (core/safety): SensitiveDetector → SafetyWriteGate → REVIEW→AES-GCM 隔离区 + HMAC 审计
                  ┌────────────────────┴─────────────────────┐
           事实源 SQLite (storage/models 27 表)       向量引擎 (Milvus 生产 / FAISS+BM25 开发)
                  └────────────────────┬─────────────────────┘
                          ProjectionOutbox（vNext→Legacy 投影同步，异步 Worker）
                  ┌────────────────────┴─────────────────────┐
            灰度控制: RolloutController(0/5/25/50/100) + ShadowReadService(双读) + RolloutReadService(canary fail-closed)
                  └────────────────────┬─────────────────────┘
                          可观测性: observability/{trace_store,audit_store,metrics}
```

**要点**：
- `app.py:create_app()` 是组合根；`startup()` 中一次性装配全部组件（安全密钥、用户规则、存储、LLM/Embedding、**检索引擎分支**、MemoryWriteService、CanonicalWriteService、RetrievalService、RolloutController、EventIngestionService、LifecycleScheduler、FormationWorker、ProjectionOutboxWorker、补偿任务）。
- **vNext 与 Legacy 通过 `ProjectionOutbox` 解耦**：vNext 写入后不直接依赖 legacy 视图，而是入队出盒，由 `ProjectionOutboxWorker` 异步投影，保证两套视图最终一致。

## 7. 核心执行流程

### 7.1 写入链路 A（Legacy）
`POST /api/memory/events` → `adapter/api.py` → `EventIngestionService.ingest()`（幂等→质量评分→`SafetyGate.route`→批存）→ `PreferenceExtractor` / `KnowledgeExtractor` 抽取 → `MemoryWriteService.upsert_memory()`（经 SafetyGate 或 `skip_write_gate`）→ `_unsafe_upsert_memory()`（DomainMemoryWriter 事务写 + `sync_memory()` 投影到向量/关键词/lookup/cache）。

### 7.2 写入链路 B（vNext Canonical）
`POST /api/memory/vnext/events` → `adapter/vnext_api.py` → `CanonicalWriteService.write()`：
```
EventGateway.submit()            # 授权/策略/幂等/冲突；状态 COMMITTED/IDEMPOTENT/CONFLICT/REVIEW/REJECTED
  → WorkingService               # 短期工作记忆
  → EpisodeService               # 中期情景(episode)
  → ExtractionTask 入队          # 触发 FormationWorker
  → _write_long_term()           # Authority facade.prepare() + memory_write_service.upsert_memory(skip_write_gate=True)
  → ProjectionOutbox 入队        # 异步投影到 legacy 视图
```

### 7.3 抽取 Worker（vNext）
`FormationWorker.execute()`：**Reflection → Candidate → Consolidation**；`mode∈{shadow, candidate-only, authority}`（`config.py:119`）控制是否真正写 Authority 长期记忆。

### 7.4 检索链路
`/api/memory/search` 或 `/api/memory/vnext/search` → `RetrievalService.retrieve()`（7 步管道：意图路由→规划→通道执行→融合重排→Scope→预算→激活日志/追踪）→ 经 `RolloutReadService.read()` 按 `mode` 选 `legacy / vnext / canary`（canary **失败回退 legacy**），`ShadowReadService.dual_read()` 在灰度期对比两套结果集（VERSION/SCOPE/POLICY_LEAK/CROSS_TENANT/FORGET_LEAK 差异）。
> 备注：RetrievalService 的 7 步管道依据 `application/retrieval_service.py` 读取归纳；其中各步的具体算法（如重排打分公式）建议后续逐函数确认，本文不展开。

### 7.5 遗忘链路
`ForgetService.execute()`：高危授权检查 → 幂等 → 定位目标 → **Authority tombstone**（`EvolutionStatus.DELETED`）→ `ProjectionOutbox` 入队（`delete, priority=100`），由 Worker 同步清理 legacy 投影。

## 10. 关键技术点

- **双层架构并存 + 灰度发布**：vNext（`application/domain`）与 Legacy（`core/retrieval`）并行；`RolloutController.LEVELS=(0,5,25,50,100)`（`rollout_service.py:20`），`canary_percent∈{5,25,50,100}`（`config.py:101`），level 0 为回滚基线；canary 按 tenant/user 身份**确定性分流**（`rollout_service.py:317`），失败 **fail-closed 回退 legacy**。
- **安全纵深（fail-closed）**：`SensitiveDetector`（规则叠加 `SafetyRuleOverlay`、归一化文本、候选消解）扫描 → `SafetyWriteGate.route()` 返回 `APPROVE/REVIEW/REJECT` → `REVIEW` 事件仅以 **AES-256-GCM 密文**落隔离区（`quarantine.py:24` `AESGCM`，密钥 32 字节=256 位，`quarantine.py:148`）→ 审计日志走 **HMAC 哈希链**（`audit_log.py`，`fingerprint_key_id`）→ 写操作受 `ApprovedWrite` 不可变令牌 `_APPROVED_WRITE_TOKEN`（`gate.py:30,90`）保护，杜绝绕过门禁直接落库。
- **分层记忆（三级级联）**：短期工作记忆 / 中期情景(episode) / 长期混合；`adapter/api.py:_apply_tiered_cascade()` 实现级联召回。
- **状态机**：记忆状态 `active/pending/archived/deleted`；演化状态 `EvolutionStatus(ACTIVE/DORMANT/SUPERSEDED/ARCHIVED/DELETED)`，遗忘用 `DELETED` tombstone 而非物理删除。
- **事件网关幂等/冲突**：`idempotency_records` + `source_hash` 去重；`GatewayStatus` 含 `CONFLICT`，冲突进入 `conflicts` 表待人工/策略裁决。
- **向量引擎可降级**：`create_vector_engine()` 按配置在 Milvus（生产）与 FAISS+BM25（开发）间切换；`MilvusHybridRetriever` 与 `HybridRetriever` 分别服务两套环境，`Reranker` 做融合重排。
- **原生嵌入（麒麟特色）**：`embedding.provider=kylin` 时通过 `so_path` 加载**原生动态库**做嵌入（`config.py:162`），契合银河麒麟 OS 本地化部署。
- **出盒（Outbox）模式**：`ProjectionOutboxWorker`（`projection_outbox.py:26`）异步将 vNext 写入投影到 legacy 视图，解耦双轨、保证最终一致。
- **可观测性内建**：`trace_store`（含 `assert_redacted` 脱敏断言，`trace_policy.py:30`）、`audit_store`、`metrics`（`InfrastructureMetrics`、`_Timer`），覆盖追踪/审计/指标。

## 11. 设计亮点

1. **组合根集中装配 + 可降级存储**：`app.py` 一处装配、环境可切换 Milvus↔FAISS，开发与生产解耦清晰。
2. **安全纵深且 fail-closed**：检测→门禁→隔离区加密→审计链，任一环节失败默认拒绝；`ApprovedWrite` 令牌杜绝「跳过门禁直写」。
3. **灰度可回滚、可双读对比**：分级放量 + 确定性分流 + `ShadowReadService` 双读差异检测 + canary 失败回退 legacy，迁移风险可控。
4. **Outbox 解耦双轨**：vNext 写入与 legacy 投影通过出盒异步同步，避免强耦合。
5. **生产强约束门禁**：`validate_production_runtime` 硬性禁止 mock/faiss、强制 768 维与 kylin/milvus，防止「开发配置误上生产」。
6. **可观测性与脱敏内建**：追踪/审计/指标原生支持，且追踪带脱敏断言，符合隐私合规。

## 13. 最终总结

Kylin MemoryHub 是一套**面向银河麒麟 OS Agent、双层架构并存、带安全门禁与灰度发布能力的本地化记忆引擎**。理解它的关键抓手只有两条主线：

1. **安全门禁主线**：`SensitiveDetector → SafetyWriteGate → REVIEW→AES-GCM 隔离区 + HMAC 审计`，是项目「安全可控」承诺的技术落点。
2. **灰度双轨主线**：vNext（`application/domain`，经 `EventGateway`/`CanonicalWriteService`/`ProjectionOutbox`）+ Legacy（`core`/`retrieval`）并行，由 `RolloutController` 分级放量、`ShadowReadService` 双读对比，是项目「可演进、可回滚」的设计核心。

**建议阅读路径**：`app.py`（看组件）→ `config.py`（看模式/生产约束）→ `adapter/`（看入口）→ `application/canonical_write.py`+`event_gateway.py`（看 vNext 主链）→ `core/memory_write.py`+`core/ingestion`（看 Legacy 主链）→ `retrieval_service.py`+`rollout_service.py`（看检索与灰度）→ `core/safety/*`（看门禁）→ `storage/*`（看持久化）。

> 一句话：**MemoryHub = 「安全门禁下的分层记忆」＋「可灰度回滚的双轨架构」**，文档滞后、以代码为准是阅读本项目时的第一原则。
