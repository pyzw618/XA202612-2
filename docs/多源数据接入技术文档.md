# 多源数据接入（清洗、标准化、质量评分）技术文档

## 1. 文档定位

本文档对应比赛方案中“多源数据整合模块”的研发范围，负责把工具执行结果、用户行为和手动配置统一转换为可供偏好记忆、知识记忆和冲突检测使用的规范事件。

比赛方案对本模块提出了三项直接要求：

1. 支持工具执行结果、用户行为数据和手动配置信息的统一接入；
2. 建立清洗、格式标准化和质量校验机制；
3. 通过标准化数据集和量化指标形成测试报告。

比赛方案的系统级指标还包括偏好提取准确率 >= 85%、知识检索召回率 >= 85%、检索响应时间 <= 500 ms 和知识冲突处理正确率 >= 88%。数据接入质量是这些指标的上游条件，但不能把接入字段准确率直接宣称为偏好提取或知识检索成绩。

当前实现位于：

```text
memory_core/ingestion/pipeline.py
evaluation/datasets/ingestion_dataset.jsonl
evaluation/scripts/evaluate_ingestion.py
```

实现只依赖 Python 标准库，便于在端侧环境运行。它与现有 `memory_core/conflict` 模块解耦，接入结果可以作为后续证据链或 `KnowledgeItem` 的输入。

## 2. 总体流程

```text
原始事件
  -> 字段别名识别
  -> Unicode 规范化、空白和控制字符清洗
  -> 敏感信息识别与脱敏
  -> 来源、事件类型、时间和 payload 标准化
  -> 必填字段、合法性、一致性、新鲜度评分
  -> canonical event + quality report
  -> 下游偏好提取、知识沉淀、冲突检测
```

管线不直接丢弃低质量事件，而是返回 `accepted`、`review` 或 `rejected` 状态。这样可以保留审计证据，并由上层决定是否入库、进入人工复核队列或只写入隔离区。

## 3. 统一事件模型

### 3.1 顶层字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event_id` | string | 事件唯一标识；缺失时由清洗后内容的 SHA-256 前缀确定性生成 |
| `source_type` | enum | `tool_result`、`user_behavior`、`manual_config` |
| `event_type` | string | 规范化事件类型，如 `tool_result`、`user_action`、`manual_config` |
| `user_id` | string | 用户标识，无法识别时留空并降低质量 |
| `session_id` | string | 会话或任务链标识，可为空 |
| `scene` | string | 作用场景，例如 `office`、`coding` |
| `task_type` | string | 任务类型，例如 `weekly_report` |
| `occurred_at` | string | UTC 时间，格式为 `YYYY-MM-DDTHH:MM:SSZ` |
| `text` | string | 可供偏好或知识抽取使用的摘要文本 |
| `payload` | object | 来源特有的结构化内容，保留工具名、状态、行为、配置键值等 |
| `schema_version` | string | 当前为 `1.0` |
| `source_hash` | string | 清洗后原始事件的 SHA-256，用于追踪和去重，不是原文存储 |
| `redactions` | array | 脱敏类型，如 `api_key`、`token`、`email`、`phone` |
| `quality` | object | 质量分数、分项分数、状态和问题列表 |

### 3.2 来源别名

输入可以使用不同字段名，管线统一映射：

| 输入别名 | 规范值 |
| --- | --- |
| `tool`、`tool_call`、`tool_call_result`、`tool_execution` | `tool_result` |
| `behavior`、`user_action`、`user_behavior` | `user_behavior` |
| `manual`、`config`、`manual_config` | `manual_config` |

事件类型为空时，按来源推导：工具来源为 `tool_result`，行为来源为 `user_action`，手动配置来源为 `manual_config`。

### 3.3 三类输入示例

工具执行结果：

```json
{
  "source": "tool_call_result",
  "user": "u-001",
  "timestamp": "2026-07-19 10:00:00+08:00",
  "tool": "file_search",
  "payload": {"status": "success", "output": "找到 3 个文件"}
}
```

用户行为：

```json
{
  "source": "behavior",
  "event_type": "action",
  "user_id": "u-002",
  "occurred_at": "2026-07-18",
  "payload": {"action": "format_change", "target": "report", "value": "Markdown"}
}
```

手动配置：

```json
{
  "source": "manual",
  "user_id": "u-003",
  "occurred_at": "2026-07-17T09:00:00Z",
  "payload": {"key": "report.format", "value": "Markdown"}
}
```

## 4. 清洗与标准化规则

### 4.1 文本清洗

1. 对字符串执行 Unicode NFKC 规范化，统一全角和半角表示；
2. 去除控制字符，保留必要的换行和制表符；
3. 把连续空白折叠为一个空格并去除首尾空白；
4. 递归处理对象和数组，不改变数字、布尔值和空值的类型；
5. 不在管线中擅自删除业务字段，未知字段仍保留在 `payload` 中。

### 4.2 时间标准化

支持 ISO 8601、带空格的日期时间、日期字符串和 Unix 秒/毫秒时间戳。无时区时间按 UTC 解释，带时区时间先转换为 UTC，输出精度截断到秒。无法解析的时间输出空字符串，并记录 `invalid:occurred_at`。

### 4.3 敏感信息

当前识别并替换：

- `api_key`、`access_key`、`token`、`secret`、`password` 等键值；
- `sk-` 开头的 API Key 形式；
- 电子邮件地址；
- 中国大陆手机号。

脱敏发生在顶层字段和嵌套 `payload` 中，输出只保留 `[REDACTED_*]` 占位符和类型标签。原始秘密值不进入 canonical event。生产环境还应按麒麟系统的安全要求补充证件号、内网地址和组织自定义密钥规则。

## 5. 质量评分与入库策略

### 5.1 分项定义

质量分数范围为 `[0, 1]`：

```text
score = 0.40 * completeness
      + 0.30 * validity
      + 0.20 * consistency
      + 0.10 * freshness
```

- `completeness`：`event_id`、`source_type`、`event_type`、`user_id`、`occurred_at`、`payload` 六个必填项的完整比例；
- `validity`：来源是否受支持、事件类型是否有效、时间是否可解析；
- `consistency`：工具事件是否包含 `tool_name`，行为事件是否包含 `action`、`target` 或 `value`，配置事件是否包含配置键或值；
- `freshness`：相对于评测参考时间，30 天内为 1.0，31 至 180 天为 0.8，181 至 365 天为 0.6，超过一年为 0.4。

### 5.2 状态阈值和硬门槛

| 状态 | 规则 | 下游动作建议 |
| --- | --- | --- |
| `accepted` | 分数 >= 0.80 且无硬门槛问题 | 写入记忆事件并允许抽取 |
| `review` | 分数 0.60 至 0.79，或来源未知、字段缺失、时间非法 | 隔离并进入复核，不直接形成长期记忆 |
| `rejected` | 分数 < 0.60，或同时缺失 `user_id` 且时间非法 | 拒绝进入记忆链路，保留审计摘要 |

敏感信息脱敏本身不会降低质量分，但会增加 `security:redacted_sensitive_value` 问题，供安全审计和下游策略使用。质量评分不替代权限校验、访问控制或向量索引删除。

### 5.3 调用方式

```python
from memory_core.ingestion import IngestionPipeline

pipeline = IngestionPipeline(reference_time="2026-07-20T00:00:00Z")
record = pipeline.process(raw_event)

if record.quality.status == "accepted":
    # 交给偏好抽取或知识沉淀模块
    consume(record.to_dict())
elif record.quality.status == "review":
    write_review_queue(record.to_dict())
```

固定 `reference_time` 适用于离线评测；线上运行不传该参数时使用当前 UTC 时间。

## 6. 评测方法

仓库已有技术方案建议使用标准化数据集、对比实验和消融实验。本模块先落地四项可复现指标：

1. **规范字段准确率**：对标注样本的 `source_type`、`event_type`、`user_id`、`occurred_at` 做 exact match；
2. **质量状态准确率**：比较 `accepted`、`review`、`rejected` 与人工金标准；
3. **敏感信息召回率**：`发现的敏感类型 ∩ 金标准类型 / 金标准类型`；
4. **处理延迟**：统计单事件处理的 mean、P50、P95、P99，检查接入开销是否远小于 500 ms 检索预算。

评测入口：

```bash
python evaluation/scripts/evaluate_ingestion.py --data evaluation/datasets/ingestion_dataset.jsonl
python evaluation/scripts/evaluate_ingestion.py --data evaluation/datasets/ingestion_dataset.jsonl --repeat 100
python evaluation/scripts/evaluate_ingestion.py --show-mistakes
```

`--repeat 100` 仅把 12 条开发样本重复 100 次用于获得 1,200 个延迟观测，并没有扩大语义样本量。

## 7. 当前实验结果

运行环境：Windows、Python 3.13.5，参考时间固定为 `2026-07-20T00:00:00Z`。数据集为仓库内自建的 12 条开发样本，覆盖三种来源、字段别名、时区转换、毫秒时间戳、缺失字段、未知来源和嵌套敏感信息。

### 7.1 正确性结果

| 指标 | 结果 | 样本量 |
| --- | ---: | ---: |
| 规范字段准确率 | 100.00% | 48 个字段断言 |
| 质量状态准确率 | 100.00% | 12 条 |
| 敏感信息类型召回率 | 100.00% | 4 个敏感类型断言 |

### 7.2 延迟结果

以下结果来自 `--repeat 100`，即 1,200 次事件处理：

| 指标 | 结果 |
| --- | ---: |
| Mean | 0.0889 ms |
| P50 | 0.0839 ms |
| P95 | 0.1189 ms |
| P99 | 0.2068 ms |

该延迟只代表清洗、标准化和评分，不包含 embedding、数据库写入、向量检索或网络调用，不能直接等同于比赛要求的端到端检索延迟。

### 7.3 现有冲突模块的关联基线

为了验证接入改动没有破坏已有能力，同时复跑了分支原有冲突评测：

| 模式 | 样本数 | 正确数 | Accuracy |
| --- | ---: | ---: | ---: |
| 结构化记忆模式 | 45 | 45 | 100.00% |
| 纯文本模式 | 45 | 44 | 97.78% |

这组结果属于冲突检测开发集，不是多源接入指标，也不是官方测试集成绩。

### 7.4 LongMemEval 真实规模接入实验

仓库本地已有 LongMemEval 的三个文件，总大小约 3.03 GB。本实验使用流式 JSON 数组解析器逐个读取问题对象，没有把完整文件加载到内存。

适配规则如下：

| LongMemEval 字段 | canonical event 映射 |
| --- | --- |
| `role=user` | `source_type=user_behavior`、`event_type=user_action` |
| `role=assistant` | `source_type=tool_result`、`event_type=tool_result` |
| `question_id` | 数据集内用户代理标识，不代表真实用户 ID |
| `haystack_session_ids` | `session_id` |
| `haystack_dates` | `occurred_at`，解析后转换为 UTC |
| `content` | `text` |
| `question_type` | `task_type` |

LongMemEval 使用 `YYYY/MM/DD (Day) HH:MM` 日期格式，接入管线增加了对应解析规则。日期不带原始时区，因此实验按 UTC 解释；生产环境必须由来源适配器提供真实时区。

运行命令：

```bash
python evaluation/scripts/evaluate_longmemeval_ingestion.py \
  --data evaluation/datasets/longmemeval/longmemeval_m_cleaned.json \
  --output evaluation/reports/longmemeval_m_ingestion.json
```

三份全量结果如下：

| 数据文件 | 文件大小 | 问题 | 会话 | 接入事件 | 吞吐（event/s） | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `longmemeval_oracle.json` | 15.39 MB | 500 | 948 | 10,960 | 2,163 | 0.313 ms | 0.936 ms | 1.089 ms |
| `longmemeval_s_cleaned.json` | 277.38 MB | 500 | 23,867 | 246,750 | 2,487 | 0.267 ms | 0.877 ms | 1.123 ms |
| `longmemeval_m_cleaned.json` | 2.74 GB | 500 | 237,655 | 2,446,993 | 2,515 | 0.253 ms | 0.843 ms | 1.032 ms |

最大文件的完整扫描耗时 972.94 秒，系统侧观察到 Python 进程峰值工作集约 180 MB。2,446,993 条事件的日期解析失败数为 0，空文本数为 779。所有事件都满足适配后的必填字段和来源一致性约束，质量状态为 `accepted`，平均质量分为 0.94。

敏感信息规则在最大文件上检测到：

| 类型 | 命中次数 |
| --- | ---: |
| `email` | 2,512 |
| `api_key` | 155 |
| `token` | 544 |
| `phone` | 12 |

共有 3,106 条事件触发至少一种脱敏规则，敏感类型命中总数为 3,223。这里统计的是规则检测量，不是有人工金标准的 Precision 或 Recall；误报和漏报必须在抽样标注后计算。

所有事件均产生 `freshness:stale_event`，因为 LongMemEval 数据时间为 2023 年，而评测参考时间固定为 2026-07-20。该现象验证了新鲜度规则，但也说明 LongMemEval 更适合作为历史记忆回放和检索数据，不应直接代表线上近期行为流量。

这组实验验证的是：

1. GB 级 JSON 的流式接入能力；
2. 用户行为和 Agent 输出两类来源的统一标准化；
3. LongMemEval 日期格式解析；
4. 敏感信息入库前规则检测；
5. 接入吞吐、延迟和内存开销。

它没有评测 LongMemEval 的问答正确率或记忆检索 Recall@K。后续需要接入检索模块，按 `answer_session_ids` 作为相关文档金标准计算 Recall@1、Recall@3、Recall@5、MRR 和 nDCG。

机器可读报告位于：

```text

evaluation/reports/longmemeval_s_ingestion.json
evaluation/reports/longmemeval_m_ingestion.json
```

## 8. 后续实验和上线前检查

当前 12 条样本只能验证规则链路，不能代表真实流量。下一轮应从脱敏后的真实日志中按来源、场景和时间分层抽样，建议至少覆盖每类来源 100 条，并固定训练、验证、回归三份集合。

建议增加以下指标和对比：

| 实验 | 目的 |
| --- | --- |
| 完整管线 vs 仅清洗 | 验证标准化和质量评分的增益 |
| 去掉敏感信息检测 | 验证安全规则的召回和误报 |
| 去掉来源一致性评分 | 验证错误 payload 是否被拦截 |
| 每个来源分别统计 | 定位工具、行为、配置的质量差异 |
| 质量分数分桶校准 | 检查高分事件是否真的更可靠 |
| 重复事件和乱序事件回放 | 验证幂等、版本和时间窗口策略 |

上线前还需要补充：

1. 与短期、中期记忆的数据流转契约和失败重试策略；
2. 真实银河麒麟环境下的文件权限、进程隔离和资源占用测试；
3. 组织自定义敏感字段及脱敏规则的配置化；
4. `source_hash` 去重窗口、事件版本和迟到事件处理；
5. 质量分数与偏好提取准确率、知识检索 Recall@K 的关联实验。

## 9. 结论和边界

本实现完成了比赛方案要求的多源统一接入、清洗、标准化和质量校验最小闭环，并以可复现脚本给出了开发集结果。它适合作为端侧记忆模块的输入适配层，不承担偏好抽取、知识检索、冲突决策或最终安全授权。正式提交前必须用组内真实脱敏数据扩大评测集，并补齐端到端检索、偏好提取和麒麟系统适配报告。
